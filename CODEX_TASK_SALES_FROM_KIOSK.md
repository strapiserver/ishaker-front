# Codex: продажи и расход из киоска (без Nayax)

22.08.2026. Бэкенд готов на **dev-Strapi** (`admin@100.114.99.86:~/DEV/ishaker/strapi`),
на прод ещё не промоучен. Заменяет модель «продажа = транзакция Nayax» на «продажа =
**фактически выданный напиток**». Отменяет часть `TELEMETRY_SALES_ENDPOINTS.md`
(телеметрийные sale-эндпоинты пустые, туда никогда не писали).

## Зачем

Кабинет Nayax — у Максима (Bro Charge LLC), своего токена у нас нет, и это блокировало
отчётность месяцами. Но киоск сам знает всё нужное в момент, когда контроллер ответил
`DrinkPreparingSuccess`: какой продукт, из какой ячейки, в какой стакан, сколько списал,
сколько взял денег. Этого достаточно и для статистики, и для расхода сырья, и для дохода.
Nayax остаётся отдельным (необязательным) источником сверки: комиссии, возвраты,
сеттлмент — только там.

**Главное правило: `source=kiosk` и `source=nayax` — это РАЗНЫЕ факты. Никогда не
складывать их в одну сумму.** Выданный напиток ≠ проведённый платёж.

## 1. Что изменилось в Strapi (уже сделано, менять не надо)

### content-type `sale` — новые поля

| поле | смысл |
|---|---|
| `sale_uuid` (unique) | Guid киоска. Ключ идемпотентности. `nayax_transaction_id` больше не required |
| `source` | `kiosk` \| `csv_harvest` \| `nayax` \| `manual` |
| `outcome` | `dispensed` \| `failed` \| `refunded` \| `unknown`. **Статистика считает только `dispensed`** |
| `occurred_at` | UTC (сервер сам конвертирует из локального времени машины) |
| `occurred_at_local` + `machine_tz` | стенные часы машины — то, что владелец точки узнаёт как «время продажи» |
| `reported_at` | когда строка доехала до Strapi (может быть на дни позже после офлайна) |
| `cell_position`, `machine_cell` | из какого контейнера |
| `product`, `product_line`, `taste`, `cup` | связи, резолвятся сервером **по ячейке**, не по id из киоска |
| `product_2`, `taste_2`, `is_mix` | микс вкусов: два контейнера по половине дозы |
| `product_name` | подпись, замороженная на момент продажи |
| `cup_size` (`full`/`medium`), `drink_volume_ml` | размер |
| `list_price` | цена по каталогу до скидки |
| `amount` | **сколько реально заплатил клиент — выручка суммируется по нему** |
| `discount_amount`, `promo_code`, `is_free` | скидки |
| `payment_method` | `CARD`/`CASH`/`FREE`/… — тип оплаты киоска, не статус эквайринга |
| `powder_g`, `water_ml`, `cups_used` | расход по рецепту |
| `addon_product`, `addon_g` | добавка из отдельного контейнера |
| `writeoffs` (json) | `[{position, product_id, grams, unit}]` — все списания напитка |
| `remains_after` (json) | `{containers:{"<позиция>": граммы}, water_ml, cups}` — остатки ПОСЛЕ пролива |
| `patch_slug` | какой патч киоска породил строку |

### эндпоинты

**`GET /api/sales-summary`** — агрегация (это то, что вам нужно для KPI и графиков).

```
GET /api/sales-summary?client=<id>&machine=<id>&from=<ISO>&to=<ISO>&group=day|product|machine|cell
```

Отвечает:

```json
{
  "range": {"from": "...", "to": "..."},
  "group": "day",
  "currency": "USD",
  "truncated": false,
  "totals": {"cups": 128, "revenue": 573.5, "free_cups": 4, "powder_g": 3840,
             "water_ml": 34560, "cups_used": 124, "avg_check": 4.48},
  "groups": [{"key": "2026-08-21", "cups": 12, "revenue": 54.0, "free_cups": 0,
              "powder_g": 360, "water_ml": 3240, "cups_used": 12}]
}
```

* фильтрует `outcome=dispensed` и `source in (kiosk, csv_harvest)` сам;
* `truncated: true` = упёрлись в лимит 20 000 строк, покажите предупреждение и попросите
  сузить период (тогда мы переведём агрегацию на SQL);
* **прав на владение НЕ проверяет** — как и все портальные чтения, ownership обязан
  проверить BFF. Наружу в браузер эндпоинт не выставлять.

**`GET /api/sales`** — обычный REST для таблицы, права `find`/`findOne` у роли
Authenticated уже есть.

**`POST /api/machines/:serial/sales`** — сюда пишет машина (Bearer `CATALOG_TOKEN` или
`machine.secret`). **Портал в продажи не пишет никогда.**

## 2. Что построить

### 2.1 `/sales` — переработка страницы

Сейчас страница показывает список Nayax-транзакций и сумму. Нужна страница про напитки.

* **KPI-строка** (из `/api/sales-summary`, не считать на клиенте):
  стаканов, выручка, средний чек, бесплатных стаканов, порошка (кг), воды (л).
* **График по дням** — стаканы + выручка, `group=day`. Ось X по `occurred_at_local`.
* **Разбивка** — переключатель `по продукту / по машине / по ячейке` (`group=`), таблица
  с долей от общего.
* **Таблица продаж** — уже есть, поменять колонки:
  время (локальное машины), машина, продукт (+ вкус), размер, ячейка, цена по каталогу,
  оплачено, способ оплаты. Бесплатные — бейджем `FREE`, микс — бейджем `MIX`.
* **Экспорт CSV** по текущему фильтру.
* **Подпись под заголовком** (обязательна, это не косметика):
  «Учитываются напитки, фактически выданные машиной. Комиссии, возвраты и сеттлмент по
  картам сюда не входят — они видны только в кабинете Nayax.»
* Блок `nayax.status` из текущего BFF оставить, но убрать с первого экрана: это теперь
  вспомогательный источник, а не основной.

### 2.2 Новый блок «Расход и остатки» на странице машины

`components/portal/machines/` — рядом с ячейками.

* За выбранный период по каждой ячейке: списано граммов (из `group=cell`), сколько
  налили стаканов.
* Текущий остаток — `machine-cell.amount_kg` (уже доступен порталу).
* **Прогноз «хватит на N дней»** = `amount_kg * 1000 / (средний расход г/сутки за период)`.
  Меньше 7 дней — жёлтым, меньше 3 — красным.
* Вода и стаканы — так же, из `totals.water_ml` / `totals.cups_used`.
* Рядом мелким: «расход рассчитан по рецепту; фактический вес может отличаться, машина
  дозирует по времени» (см. п. 4).

## 4. Точность: что нужно честно показать пользователю

1. **`powder_g` — номинал, не взвешено.** Машина дозирует порошок по времени
   (`граммы / conversion_factor`), а по полевому замеру 43 из 67 ячеек не откалиброваны,
   разброс CF 1.5–6.7 при среднем 4.42. Реальный расход может отличаться в полтора раза.
   Поэтому: расход по рецепту — планирование, `remains_after` — измеренная правда.
2. **Вода в `water_ml` тоже номинал.** Реальный расход воды меряет счётчик MCU, он
   приезжает в `remains_after.water_ml` (и уменьшается по факту).
3. **Часы киосков уходят на часы.** Показывать `occurred_at_local`; сортировать и
   фильтровать по `occurred_at` (UTC). Строки с подозрительным временем сервер помечает
   `raw.clock_suspect` — при желании покажите бейдж.
4. **Бесплатные стаканы считаются в стаканах и не считаются в деньгах** — не прячьте их,
   владельцы точек по ним ловят злоупотребления.
5. `truncated: true` — не рисуйте график: он неполный.

## 5. Чего не делать

* Не складывать `source=kiosk` и `source=nayax`.
* Не писать в `sale` из портала (даже «ручную корректировку» — для этого будет `manual`
  и отдельная задача).
* Не трогать `machine-cell.amount_kg` при отображении расхода. Остатком владеет цепочка
  портал↔машина (патч 33); лишний писатель уронит синк.
* Не строить сверку с Nayax — токена по-прежнему нет.

## 6. Готово, когда

* `/sales` за произвольный период показывает стаканы/выручку/средний чек, график по дням
  и разбивку по продукту, машине и ячейке; цифры сходятся с `/api/sales-summary`.
* На странице машины виден расход по ячейкам и прогноз «на сколько хватит».
* Клиент A не может увидеть данные клиента B ни через `machineId`, ни через `client`.
* Пустое состояние честное: «машина ещё не присылает продажи» (патч раскатан не везде),
  а не «$0.00».

# Дополнение 26.08.2026 — списание остатков и что осталось поправить

Реализацию приняли, ниже правки после ревью и одно изменение поведения бэкенда.

## A. Бэкенд теперь сам списывает порошок, воду и стаканы

`POST /api/machines/:serial/sales` при каждой **принятой** продаже двигает остатки —
без Nayax и без второго канала:

* порошок → `machine-cell.amount_kg` по каждому задетому контейнеру (включая обе
  половины микса и добавку — берётся из `writeoffs`);
* вода → `machine.water_amount_liters` (кроме `water_type = mains` — там считать нечего);
* стаканы → `machine.cups_amount`.

Два режима: если продажа принесла `remains_after` (счётчики самой машины после пролива) —
значения **принимаются как есть**; если нет — вычитается расход по рецепту. Дубликаты
остатки не двигают, продажи старше 24 часов — тоже (иначе бэкфилл CSV за 10 месяцев
обнулил бы весь парк). В ответе появилось поле `inventory` с тем, что реально изменилось.

**Что это значит для фронта:** остаток в блоке «Расход и остатки» теперь меняется сам,
без участия портала и без ожидания 5-минутного тика машины. Ревизии (`rev`, `water_rev`,
`cups_rev`) при этом НЕ растут — правки из портала по-прежнему главнее (патч 33/41).
Ничего менять не нужно, но кэшировать остаток на длинный TTL больше нельзя.

## B. Что поправить в `MachineConsumptionSection.tsx`

1. **`water_type === "mains"` не обработан.** У машины на водопроводе
   `water_amount_liters` пустой, и блок «Water» показывает `0.0 L remaining` с красным
   прогнозом «0 days» — ложная тревога на каждой такой машине. Поле уже есть в типе
   `Machine` и используется в `WaterDialogContent`/`MachineHealthStrip`. Для mains:
   показывать «Mains water» вместо остатка и прогноза, расход (`water_ml`) оставить.
2. **Стаканы на машинах без диспенсера.** Там `cups_used` всегда 0, а `cups_amount`
   пустой — прогноз тоже уходит в красный. Если расхода нет и остаток пустой, показывать
   «—», а не «0 days».
3. **Прогноз делит на весь период.** `forecast(remaining, used, period)` считает, что
   машина отчитывалась все 30/90 дней. Пока патч раскатывается, у машины будет 3 дня
   данных в 30-дневном окне, и «хватит на 200 дней» — это неправда в три раза.
   Делить на фактическое число суток с продажами: у `group=day` это `groups.length`
   (или разница между первым и последним ключом), минимум 1. Если суток меньше трёх —
   рядом с прогнозом ставить пометку, что данных мало.

## C. Мелочи

* В разбивке `group=cell` микс считается стаканом у обоих контейнеров, поэтому сумма
  колонки «Cups» по ячейкам больше `totals.cups`. Это осознанно (иначе не видно, что
  ячейка участвовала), но в шапке колонки стоит написать «участий», а не «стаканов».
* `/sales` доступна только клиентской сессии. Флотового обзора для админа нет —
  отдельная задача, если понадобится.
* `outcome=failed` в схеме есть, но producer-а пока нет: патч киоска шлёт только
  `dispensed`. Пустой фильтр по failed — это норма, а не баг.
